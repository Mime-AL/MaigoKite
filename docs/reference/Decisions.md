# NanamiGopher 架构决策记录（ADR）

> 本文档记录了 NanamiGopher 项目中的关键架构决策及其背景和后果，供团队成员查阅和追溯。

---

## ADR 格式说明

每条架构决策记录包含以下部分：

| 字段 | 说明 |
|------|------|
| **标题** | 决策的简要描述，格式为 `ADR-NNN: 决策主题` |
| **状态** | 决策当前的生命周期状态：`提议` / `已采纳` / `已弃用` / `待定` |
| **上下文** | 做出该决策时面临的问题、约束条件和候选方案 |
| **决策** | 最终选择的方案和理由 |
| **后果** | 该决策带来的影响，包括优势、劣势和风险 |

## ADR-001: 选择 Go 作为 API Gateway 语言

- **状态：** 已采纳
- **日期：** 2025-01-15
- **上下文：** API Gateway 需要承担路由转发、鉴权、限流、协议转换和高并发连接管理职责。候选语言包括 Go、Rust、Node.js 和 Java。要求：高并发处理能力、低内存占用、编译部署简单、生态成熟。
- **决策：** 选择 Go 语言配合 Gin 框架作为 API Gateway 的实现。
- **后果：**
  - **优势：** Go 的 goroutine 模型天然适合高并发场景；Gin 框架轻量高效；单二进制文件部署简单；与系统底层交互性能好。
  - **劣势：** 在 AI/ML 领域的生态不如 Python；部分高级抽象需要自行实现。
  - **风险：** 团队 Go 经验不足时需要学习成本。

## ADR-002: 选择 Python 作为 Agent Core 语言

- **状态：** 已采纳
- **日期：** 2025-01-15
- **上下文：** Agent Core 需要与主流大语言模型 API 对接、实现复杂的推理逻辑、集成记忆系统和向量数据库。候选语言包括 Python、TypeScript 和 Rust。要求：丰富的 AI/ML 生态、快速的原型开发能力、社区支持完善。
- **决策：** 选择 Python 作为 Agent Core 的主要实现语言。
- **后果：**
  - **优势：** Python 拥有最完善的 AI/ML 生态（LangChain、LlamaIndex、HuggingFace 等）；大模型 API 的官方 SDK 普遍优先支持 Python；开发效率高，适合快速迭代。
  - **劣势：** 运行时性能不如编译型语言；GIL 限制了多线程并发。
  - **风险：** 对于 CPU 密集型任务可能需要引入多进程或异步编程来弥补性能瓶颈。

## ADR-003: 选择 Vue 3 + Vite 作为前端框架

- **状态：** 已采纳
- **日期：** 2025-01-20
- **上下文：** 前端需要支持复杂的交互界面（对话列表、检查器面板、工具配置等），同时要求良好的开发体验和构建性能。候选方案包括 React + Webpack、Vue 3 + Vite 和 Svelte。
- **决策：** 选择 Vue 3（Composition API）配合 Vite 构建工具。
- **后果：**
  - **优势：** Vue 3 的响应式系统和 Composition API 适合大型复杂应用；Vite 提供极速的热更新；学习曲线平缓；与 Electron 集成成熟。
  - **劣势：** 相比 React，生态插件数量和第三方库丰富度略低。
  - **风险：** 团队若已有 React 经验，迁移成本需要考虑。

## ADR-004: 选择 Electron 作为桌面端框架

- **状态：** 已采纳
- **日期：** 2025-01-20
- **上下文：** 需要提供跨平台的桌面客户端，要求支持本地文件系统访问、系统托盘、通知等原生能力。候选方案包括 Electron、Tauri 和 Neutralino.js。
- **决策：** 选择 Electron 作为桌面端框架。
- **后果：**
  - **优势：** 生态成熟，社区资源丰富；与 Web 前端技术栈完全兼容；支持所有操作系统；调试工具链完善。
  - **劣势：** 内存占用较高（每个窗口一个 Chromium 实例）；安装包体积较大。
  - **风险：** 未来可考虑 Tauri 作为轻量级替代方案，但当前阶段 Electron 的稳定性更有保障。

## ADR-005: 四层工具架构设计

- **状态：** 已采纳
- **日期：** 2025-02-01
- **上下文：** Agent 需要调用多种工具完成任务，工具数量随项目演进会快速增长。需要一个清晰的层级结构来组织和管理工具，确保性能、安全性和可扩展性。候选方案包括扁平化管理、两层级（原生/MCP）和四层级。
- **决策：** 采用四层工具架构：Runtime 内核层 → 高频原生 Tool 层 → 低频原生 Tool 层 → MCP Tool 层。
- **后果：**
  - **优势：** 层级清晰，Agent 可按优先级依次查找和调用工具；Runtime 内核工具保证最低延迟；原生工具适合稳定且常用的能力；MCP 工具支持动态扩展和远程服务集成。
  - **劣势：** 增加了架构复杂度；需要维护统一的工具注册和发现机制。
  - **风险：** 层级边界可能随着功能增长变得模糊，需要定期审查和调整。

## ADR-006: Embedding Provider 工厂模式抽象

- **状态：** 已采纳
- **日期：** 2025-02-10
- **上下文：** 系统需要支持多种文本嵌入模型（BGE-M3、OpenAI ada-embeddings、GTE 等），以便在不同场景和成本约束下灵活切换。如果硬编码具体模型，后续替换成本极高。
- **决策：** 定义 `EmbeddingProvider` 接口，通过工厂模式根据配置动态创建对应的 Provider 实例（BGE-M3 为默认值）。
- **后果：**
  - **优势：** 新增 Embedding 后端只需实现接口并注册到工厂；配置驱动切换，无需修改业务代码；便于单元测试时 mock 不同的后端。
  - **劣势：** 接口设计和抽象层增加了一定的开发复杂度。
  - **风险：** 不同 Provider 的参数和响应格式差异可能导致适配层代码膨胀，需要保持接口简洁。

## ADR-007: 记忆系统与知识库分离

- **状态：** 已采纳
- **日期：** 2025-02-15
- **上下文：** Agent 需要管理两类信息：一是对话过程中的短期记忆和情景记忆（与当前任务相关），二是长期积累的知识文档（与任务解耦）。如果混在一起，会导致检索效率低下和数据结构混乱。
- **决策：** 将 IMemorySystem（短期记忆、会话记忆、情景记忆、用户画像）与 IKnowledgeBase（文档存储、向量检索、全文搜索）设计为两个独立的子系统，通过统一的 Agent Runtime 协调调用。
- **后果：**
  - **优势：** 关注点分离，各自可独立优化；记忆系统侧重实时性和上下文窗口管理，知识库侧重文档生命周期和语义检索；便于按需启用或禁用特定模块。
  - **劣势：** 两个系统之间的数据同步和一致性需要额外处理。
  - **风险：** 初期实现复杂度增加，需要在 Phase 1 和 Phase 2 分阶段落地。

## ADR-008: 先截断后检测的安全过滤策略

- **状态：** 已采纳
- **日期：** 2025-02-20
- **上下文：** 工具输入需要进行安全检查，防止恶意注入和缓冲区溢出。如果在截断之前做完整的内容检测，对于超大输入会消耗大量计算资源且拖慢响应速度；如果只截断不检测，则存在安全风险。
- **决策：** 采用"先截断后检测"的策略：首先对输入进行长度截断，然后再对截断后的内容进行安全检测和清理。
- **后果：**
  - **优势：** 截断优先保证了处理的可预测性和性能上限；检测范围缩小到截断后的内容，降低计算开销；避免了对超长输入的完整扫描。
  - **劣势：** 恶意内容如果被截断在前半段，后半段的正常内容仍可能被误伤。
  - **风险：** 需要根据实际场景调整截断阈值和检测规则的平衡。

## ADR-009: SQLite + FTS5 默认存储方案

- **状态：** 已采纳
- **日期：** 2025-02-25
- **上下文：** 系统需要持久化存储对话记录、工具调用日志、记忆数据和知识文档。候选方案包括 PostgreSQL、MongoDB、SQLite 和嵌入式键值存储。要求：开箱即用、零运维、支持全文检索、适合单机部署。
- **决策：** 选择 SQLite 作为默认存储引擎，结合 FTS5 扩展提供全文检索能力。Phase 3 引入 ChromaDB 作为向量存储的可选方案。
- **后果：**
  - **优势：** SQLite 零配置、单文件部署，非常适合开发和中小规模生产环境；FTS5 提供高效的关键词全文检索；迁移到 PostgreSQL 的成本较低（SQL 兼容性高）。
  - **劣势：** 并发写入能力有限；不适合分布式部署场景。
  - **风险：** 当数据量超过一定阈值（预计 10GB+）时，需要考虑迁移到更强大的数据库。

## ADR-010: 三栏布局 UI 设计

- **状态：** 已采纳
- **日期：** 2025-03-01
- **上下文：** 前端界面需要同时展示对话内容、Agent 执行过程和工具调用详情。单栏布局信息密度不足，两栏布局无法兼顾对话和检查器，需要一种能同时呈现多维度信息的布局方案。
- **决策：** 采用三栏布局：左侧为导航与会话列表，中间为主对话区域，右侧为 Inspector（检查器）面板，展示 SubAgent 状态、工具调用链和实时事件流。
- **后果：**
  - **优势：** 信息层次清晰，用户可以同时关注对话内容和 Agent 内部执行状态；右侧面板可折叠，适应不同屏幕尺寸；符合开发者工具的使用习惯（类似 IDE 布局）。
  - **劣势：** 在小屏幕设备上三栏同时展示体验较差，需要响应式设计适配。
  - **风险：** 右侧检查器的信息密度较高，需要精心设计可视化方式以避免信息过载。
